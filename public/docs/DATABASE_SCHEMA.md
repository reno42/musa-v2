## Architecture: JSONB-Hybrid (Document-over-Postgres)

The Design Editor uses a **JSONB-hybrid pattern**. Instead of normalized relational tables, most entities are stored as JSON blobs inside the `data` column. Only minimal top-level columns exist for querying and filtering.

```
┌─────────────────────────────────────────────────────┐
│                 templates table                      │
│                                                     │
│  id (text PK)     → "tpl_a1b2c3d4e5f6"             │
│  name (text)      → "My Design"                     │
│  workspace_id     → "ws_x1y2z3..."                  │
│  user_id (uuid)   → FK → auth.users                 │
│  data (jsonb)     → ┌──────────────────────────┐   │
│  created_at       → │ canvas: { objects[],      │   │
│  updated_at       → │   viewport }              │   │
│                     │ frames: [ Frame[] ]       │   │
│                     │ styles: [ Style[] ]       │   │
│                     │ comments: [ Comment[] ]   │   │
│                     │ versions: [ Version[] ]   │   │
│                     │ variables: { collections, │   │
│                     │   variables, bindings }   │   │
│                     │ components: [ Component[] ]│  │
│                     │ metadata: { createdAt,    │   │
│                     │   updatedAt, createdBy }  │   │
│                     └──────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

**Why this pattern?**
- The entire DesignTemplate is a self-contained document (like a Figma file)
- Frames, styles, comments, versions, variables are all embedded — no JOINs needed
- The `data` column is the single source of truth for template state
- Supabase upserts replace the entire document atomically

## Tables

### `templates`

| Column | Type | Default | Nullable | Description |
|--------|------|---------|----------|-------------|
| `id` | `text` | (app-generated: `tpl_` + uuid12) | NO | Primary key. Format: `tpl_xxxxxxxxxxxx` |
| `name` | `text` | `"Untitled"` | NO | Template name (set at creation, updatable) |
| `workspace_id` | `text` | `null` | YES | References `workspaces.id`. Format: `ws_xxxxxxxxxxxx` |
| `data` | `jsonb` | full DesignTemplate object | NO | **The entire template state.** See data structure below. |
| `user_id` | `uuid` | `null` | YES | FK → `auth.users`. Only set if valid UUID. |
| `created_at` | `timestamptz` | (auto) | NO | `[VERIFY]` Auto-generated by Supabase default? |
| `updated_at` | `timestamptz` | (app-set on write) | NO | Set to `new Date().toISOString()` on every upsert |

#### `data` JSONB Structure

```typescript
{
  id: string;          // "tpl_xxx" (redundant with top-level id)
  workspaceId: string; // "ws_xxx" (redundant with top-level workspace_id)
  name: string;        // redundant with top-level name
  width: number;       // canvas width (default 1080)
  height: number;      // canvas height (default 1080)
  canvas: {
    version?: string;  // Fabric.js version
    objects: FabricObject[];  // ← THE CANVAS LAYERS
    background?: string;
    viewport: { x: number, y: number, zoom: number };
  };
  frames: Frame[];     // Frame objects (separate from canvas.objects)
  styles: Style[];
  comments: Comment[];
  versions: Version[];
  variables: {
    collections: { id: string, name: string }[];
    variables: { id: string, collectionId: string, name: string, value: any }[];
    bindings: Record<string, any[]>;
  };
  components: Component[];
  metadata: {
    createdAt: string;
    updatedAt: string;
    createdBy?: string;
  };
}
```

#### `FabricObject` structure (in `canvas.objects[]`)

```typescript
{
  type: string;           // "rect", "textbox", "group", "image", etc.
  layerName?: string;     // User-assigned layer name for MCP targeting
  layerId?: string;       // Unique layer identifier
  frameId?: string;       // Link to parent frame (for frame-bound objects)
  isFrameVisual?: boolean; // Marker: this object is a frame visual
  isFrameBg?: boolean;     // Marker: this is the background rect of a frame
  name?: string;
  left?: number;  top?: number;
  width?: number; height?: number;
  scaleX?: number; scaleY?: number;
  angle?: number;
  fill?: string;  stroke?: string;  strokeWidth?: number;
  opacity?: number;
  visible?: boolean;  locked?: boolean;
  rx?: number;  ry?: number;
  text?: string;  fontSize?: number;  fontFamily?: string;
  src?: string;  // image URL
  path?: any[];  // SVG path data
  objects?: FabricObject[];  // nested objects (groups)
  isClosedPath?: boolean;
  imageFilters?: any;  styleId?: string;
  componentId?: string;  isComponentInstance?: boolean;
  constraints?: any;  autoLayout?: any;
  resizingMode?: string;  overrides?: any;
  [key: string]: any;     // Fabric.js extras
}
```

#### `Frame` structure (in `data.frames[]`)

```typescript
{
  id: string;        // "frame_xxxxxxxxxxxx"
  templateId: string;
  name: string;
  x: number;  y: number;
  width: number;  height: number;
  fill?: string;    // background color
  opacity?: number;
  order: number;     // z-order within frames
  objects: FabricObject[];  // objects contained in this frame
}
```

**⚠️ Architectural Note:** Frames are stored in `data.frames[]` separate from `data.canvas.objects[]`. This is a **known gap (P0.3)** — Puppeteer renderer only processes `canvas.objects`, not `frames[]`. The proposed fix is to store frames as canvas objects with `isFrameVisual: true`.

## CRUD Operations Map

| Operation | Table | Method | Notes |
|-----------|-------|--------|-------|
| List templates | `templates` | `.select("*")` + `.order("updated_at")` + `.range()` | Workspace search filter applied client-side |
| Get template | `templates` | `.select("*").eq("id", id).single()` | Falls back to in-memory store |
| Create/Update template | `templates` | `.upsert(row)` | Entire document replace |
| Delete template | `templates` | `.delete().eq("id", id)` | + in-memory store cleanup |
| List workspaces | `workspaces` | `.select("*").order("updated_at")` | Client-side ownerId/membership filtering |
| Create/Update workspace | `workspaces` | `.upsert(row)` | Members stored inside JSONB `data` |
| Delete workspace | `workspaces` | `.delete().eq("id", id)` | + cascading template deletion in-memory |

## In-Memory Store Fallback

When Supabase is not configured (env vars missing or contain `"your-project"` placeholder), the entire API falls back to an **in-memory Map-based store** (`api/src/services/store.ts`). This means:

- The system works **without** Supabase for development
- All CRUD operations go through `templates.ts` which wraps both Supabase + in-memory
- The in-memory store is NOT persistent (lost on server restart)
- Supabase upsert is fire-and-forget (best effort) — failures are logged but don't block responses
