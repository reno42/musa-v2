## 🔴 P0 — CRÍTICO (bloquea funcionalidad)

### P0.1: `em()` destruye precisión decimal
**Archivo:** `src/components/PropertiesPanel.tsx:12`
**Función:** `const em = (n: number) => Math.round(n);`
**Problema:** `em()` se usa en fieldX, fieldY, fieldW, fieldH, fieldAngle, fieldRx, fieldRy. `Math.round()` trunca TODA precisión decimal. El store/API preserva decimales, pero la UI los destruye al editar.
**Fix:** Eliminar `em()`. Mostrar `n.toFixed(1)` en display, usar `n` crudo en commit.
**Impacto:** 0.1px precision, rotation 0.1°, border-radius exacto — TODO pierde precisión.

### P0.2: `batch_update` con `objects[]` destruye el canvas
**Archivo:** `netlify/functions/mcp.mjs` (tool `batch_update`)
**Problema:** Cuando se pasan objetos por `objects[]`, reemplaza el canvas entero en vez de hacer merge. Si solo quieres cambiar 1 objeto de 100, los otros 99 se pierden.
**Fix:** Si `objects[]` tiene objetos con `layerName`, hacer merge por layerName. Si no tienen layerName, append.
**Impacto:** Rompe actualizaciones batch parciales. Inutilizable para edición programática.

### P0.3: Frames no persisten → `render_frame` siempre falla
**Archivos:** `api/src/services/store.ts`, `netlify/functions/mcp.mjs` (tool `create_frame`)
**Problema:** `create_frame` guarda frames en `frames[]` separado de `canvas.objects[]`. Puppeteer solo renderiza `canvas.objects`. La metodología que SÍ funciona es `update_template` con `isFrameVisual:true`.
**Fix:** Unificar frames como objetos canvas visuales con `isFrameVisual:true` y `frameId`. O hacer que el renderer también procese `frames[]`.
**Impacto:** 13 tests de frames fallan. Sin frames, no hay artboards. Sin artboards, no es Figma.

### P0.4: Sin validación de rangos en `transform_object`
**Archivo:** `netlify/functions/mcp.mjs` (tool `transform_object`)
**Problema:** opacity acepta -1 y 2. angle acepta 999999. width/height aceptan negativos. Sin límites = canvas corrupto.
**Fix:** Validar: opacity 0-1, angle 0-360 (normalizar), width/height >0, scaleX/scaleY en rango razonable.
**Impacto:** Datos corruptos en store. Render falla silenciosamente.

### QODER ANALYSIS: P0.1 — `em()` destroys decimal precision

**¿Confirmado?:** SI

**Causa raíz:** `const em = (n: number) => \`${Math.round(n)}\`;` en [PropertiesPanel.tsx:12](file:///c:/Users/Renzo/.openclaw/workspace/design-main/src/components/PropertiesPanel.tsx#L12). `Math.round()` trunca TODA precisión decimal. Se usa en 7 campos:
- `fieldX` (línea 102), `fieldY` (línea 103) — posición
- `fieldW` (línea 104), `fieldH` (línea 105) — dimensiones (width × scaleX, height × scaleY)
- `fieldAngle` (línea 106) — rotación
- `fieldRx` (línea 111) — border radius
- Canvas width/height (líneas 86-87)
- `commitScale()` — recalcula scaleX/scaleY al editar dimensiones, usando `em()` → pierde decimales

El store/API preserva decimales (ej: left=100.5), pero al editar desde el PropertiesPanel, `em()` redondea el valor mostrado y el valor commiteado. Esto significa que CADA vez que el usuario edita una propiedad desde el panel, pierde precisión.

**Archivos a modificar:**
- `src/components/PropertiesPanel.tsx`

**Funciones a modificar:**
- `em()` (línea 12) → reemplazar implementación
- `fieldX`, `fieldY`, `fieldW`, `fieldH`, `fieldAngle` (líneas 102-106) → usar nuevo formato
- `fieldRx` (línea 111) → usar nuevo formato
- `commitScale()` → eliminar uso de `em()`, preservar decimales
- Canvas width/height display (líneas 86-87) → usar nuevo formato

**Approach:**
1. Cambiar `em()` a `const em = (n: number) => n.toFixed(1)` — preserva 1 decimal para display
2. Para los commit handlers (`commitScale`, `commit` de width/height), usar el valor numérico crudo (`Number(v)`) SIN pasar por `em()`
3. Agregar `step="0.1"` a los inputs numéricos para UX de precisión
4. Para angle: normalizar a `angle % 360` en el commit (bonus: fix CAT1-003 angle normalization)
5. Para fieldW/fieldH: la fórmula existente `(obj.width ?? 0) * (obj.scaleX ?? 1)` ya es correcta; solo cambiar la capa de display

**Riesgo de BD:** NO — cambio exclusivo de UI. No altera esquema ni datos.

**Tiempo estimado:** 25 minutos

### QODER ANALYSIS: P0.2 — `batch_update` with `objects[]` destroys canvas

**¿Confirmado?:** SI

**Causa raíz:** [mcp.mjs:854-857](file:///c:/Users/Renzo/.openclaw/workspace/design-main/netlify/functions/mcp.mjs#L854-L857). Cuando `params.objects` está presente, el handler REEMPLAZA el canvas entero:
```js
updates.canvas = { objects, viewport: { x: 0, y: 0, zoom: 1 } };
```
Esto destruye todos los objetos existentes. Si el template tenía 100 objetos y pasas 1 objeto nuevo, los otros 99 se pierden. El test CAT9-010 confirma: "Template original tenía 7 objetos; después de batch_update con 1 objeto → solo queda ese objeto."

Además, `viewport` se resetea a `{x:0, y:0, zoom:1}`, perdiendo el estado de pan/zoom del usuario.

**Archivos a modificar:**
- `netlify/functions/mcp.mjs`

**Funciones a modificar:**
- `batch_update` handler (líneas 841-874)

**Approach:**
1. Obtener el template actual ANTES de construir updates
2. Si `params.objects` existe, hacer merge inteligente:
   - Para cada objeto nuevo con `layerName`, buscar si ya existe en `canvas.objects[]` con el mismo `layerName`. Si existe → reemplazar (update). Si no → append (add).
   - Si los objetos NO tienen `layerName`, hacer append al array existente (nunca replace).
3. Preservar el `viewport` existente (no resetear a default)
4. El merge debe operar sobre `tpl.canvas.objects` existente, NO sobre `params.objects`

**Riesgo de BD:** NO — cambio en lógica de merge, sin alterar schema. Pero CRÍTICO: cada invocation de batch_update con `objects[]` actualmente destruye datos. Este fix es URGENTE.

### QODER ANALYSIS: P0.3 — Frames don't persist → `render_frame` always fails

**¿Confirmado?:** SI (con matices)

**Causa raíz:** Arquitectura dual inconsistente. El sistema tiene DOS lugares donde puede vivir un frame:
1. `tpl.frames[]` — array separado, manejado por `store.createFrame()` en [store.ts:130-145](file:///c:/Users/Renzo/.openclaw/workspace/design-main/api/src/services/store.ts#L130-L145). `create_frame` MCP handler ([mcp.mjs:1370-1383](file:///c:/Users/Renzo/.openclaw/workspace/design-main/netlify/functions/mcp.mjs#L1370-L1383)) usa esta ruta.
2. `canvas.objects[]` con `isFrameVisual: true` y `frameId` — creado por el frontend (`useCanvas.ts → createFrame()`). El renderer tiene fallback para esta ruta en [render.mjs:89-101](file:///c:/Users/Renzo/.openclaw/workspace/design-main/netlify/functions/render.mjs#L89-L101).

El problema: `create_frame` MCP NUNCA crea el objeto visual en `canvas.objects[]`. Solo escribe en `tpl.frames[]`. El renderer primero busca en `tpl.frames[]`, y luego en `canvas.objects` (isFrameVisual). Pero como el store es Map-based in-memory + Supabase, y las Edge Functions son stateless, hay inconsistencia en qué datos sobreviven entre invocaciones.

Los tests muestran comportamiento INCONSISTENTE:
- CAT6-002: `create_frame` funciona, `list_frames` retorna frames (template `tpl_d27a212e-cb0`)
- CAT7-007: `create_frame` NO persiste, `list_frames` retorna `[]` (template `tpl_4e1485e7-121`)

Esto sugiere que el in-memory store a veces sobrevive entre requests (misma instancia de Lambda) y a veces no. En una Edge Function fría, `store.templates` está vacío, y `templates.updateTemplate()` hace `Object.assign(fromDb, updates)` sobre el objeto de Supabase, setea `fromDb.frames`, y luego `upsertSupabase(tpl)` guarda el objeto completo. Esto DEBERÍA persistir frames a Supabase. Pero el test CAT7-007 dice que no.

Hipótesis más probable: `templates.updateTemplate()` cuando el store está frío (línea 162-175 de templates.ts):
1. `store.updateTemplate(id, updates)` → undefined (store vacío)
2. `getFromSupabase(id)` → carga el template de Supabase
3. `Object.assign(fromDb, updates)` → `fromDb.frames = tpl.frames` (pero `tpl.frames` viene del paso 1 del create_frame handler, que era el objeto en memoria)
4. `store.updateTemplate(id, fromDb)` → `this.templates.get(id)` sigue siendo undefined (no estaba en el Map), así que `store.updateTemplate` retorna undefined también
5. `upsertSupabase(tpl, userId)` → tpl = fromDb con frames seteados → esto sí persiste

Entonces los frames DEBERÍAN persistir a Supabase. Pero `list_frames` hace `templates.getTemplate(id)` que puede:
- Si el store está caliente → devolver del Map (que tal vez no tiene los frames porque se perdieron en un cold start)
- Si el store está frío → `getFromSupabase(id)` → debería tener los frames

El fix correcto es: **unificar frames como objetos canvas visuales con `isFrameVisual: true`**. Esto es lo que el frontend YA hace, y es lo que el renderer espera como fallback. 

**Archivos a modificar:**
- `netlify/functions/mcp.mjs` — `create_frame` handler
- `api/src/services/store.ts` — `createFrame()` method (opcional, para consistencia)

**Funciones a modificar:**
- `create_frame` handler ([mcp.mjs:1370-1383](file:///c:/Users/Renzo/.openclaw/workspace/design-main/netlify/functions/mcp.mjs#L1370-L1383))
- `store.createFrame()` ([store.ts:130-145](file:///c:/Users/Renzo/.openclaw/workspace/design-main/api/src/services/store.ts#L130-L145))

**Approach:**
1. En `create_frame` MCP handler, después de crear el frame vía `store.createFrame()`:
   - Crear un objeto visual en `tpl.canvas.objects` con:
     ```js
     {
       type: "rect",
       layerName: `frame_${frame.id}`,
       frameId: frame.id,
       isFrameVisual: true,
       isFrameLabel: false,
       frameName: frame.name,
       frameFill: frame.fill,
       frameStroke: "#6366f1",
       left: frame.x, top: frame.y,
       width: frame.width, height: frame.height,
       fill: frame.fill || "#ffffff",
       stroke: "#6366f1",
       strokeWidth: 1,
       rx: 0, ry: 0,
       scaleX: 1, scaleY: 1, angle: 0, opacity: 1, visible: true,
     }
     ```
2. Modificar `store.createFrame()` para que TAMBIÉN cree el objeto visual (o delegar al handler MCP)
3. El renderer YA tiene el fallback en `prepareFrameRender()` (línea 89-101), así que al existir `isFrameVisual` en `canvas.objects`, el render funcionará.
4. Mantener compatibilidad: `tpl.frames[]` sigue existiendo para metadata/listing, pero el render usa `canvas.objects`.

**Riesgo de BD:** BAJO — No se altera el schema de Supabase. Se agregan objetos al campo `data` JSON (que es JSONB). Los frames existentes en `tpl.frames[]` no se pierden. Pero REQUIERE MIGRACIÓN DE DATOS si hay frames existentes sin objeto visual (se puede hacer on-the-fly en el handler).

**Tiempo estimado:** 60 minutos

### QODER ANALYSIS: P0.4 — No range validation in `transform_object`

**¿Confirmado?:** SI

     throw { code: -32602, message: "scaleY cannot be 0" };

     throw { code: -32602, message: "strokeWidth must be >= 0" };
   if (rest.fontSize !== undefined && rest.fontSize <= 0)
     throw { code: -32602, message: "fontSize must be > 0" };
   ```

### QODER ANALYSIS: P1.3 — `diff_template` doesn't detect changes

**¿Confirmado?:** SI

**Causa raíz:** Race condition auto-snapshot. Cada handler MCP que modifica datos llama `autoSnapshot(params.templateId, method)` al FINAL (después de persistir). Esto significa que después de una mutación, el snapshot más reciente YA incluye los cambios. Cuando `diff_template` compara "último snapshot" vs "estado actual", ambos son idénticos → 0 cambios.

El flujo actual:
1. `transform_object` modifica fill de #FF0000 a #00FF00
2. Persiste a Supabase
3. `autoSnapshot(templateId, "transform_object")` → guarda snapshot con fill=#00FF00
4. Usuario llama `diff_template` → compara snapshot (fill=#00FF00) vs current (fill=#00FF00) → 0 cambios

Las funciones `compareValues()` ([mcp.mjs:651-670](file:///c:/Users/Renzo/.openclaw/workspace/design-main/netlify/functions/mcp.mjs#L651-L670)) y `compareTemplates()` ([mcp.mjs:673-690](file:///c:/Users/Renzo/.openclaw/workspace/design-main/netlify/functions/mcp.mjs#L673-L690)) son correctas — el problema es cuándo se toma el snapshot.

**Archivos a modificar:**
- `netlify/functions/mcp.mjs`

**Funciones a modificar:**
- `autoSnapshot()` helper (línea 704-706)
- `diff_template` handler (líneas 1472-1480)
- TODOS los handlers que llaman `autoSnapshot` (líneas 766, 783, 973, 997, 1018, 1038, 1061, 1264, 1286, 1314, 1340, 1381, 1409, 1420)

**Approach:**
1. **Opción A (recomendada):** Mover `autoSnapshot()` al INICIO de cada handler mutante, ANTES de modificar datos. Así el snapshot captura el estado pre-mutación.
   - Esto requiere refactorizar cada handler para: snapshot → modificar → persistir
   - Pero es el approach más correcto semánticamente
2. **Opción B:** Hacer que `diff_template` compare contra el penúltimo snapshot (snapshot[-2] vs current) en vez del último. Más frágil.
3. **Opción C:** Que `autoSnapshot` tome el snapshot ANTES de persistir, no después. Requiere obtener el template, snapshotearlo, luego modificarlo.

La Opción A es la más limpia:
```js
// En cada handler mutante:
autoSnapshot(params.templateId, method); // ← ANTES de modificar
// ... modificar y persistir ...
```

**Riesgo de BD:** NO — cambio de lógica de snapshot timing.

**Tiempo estimado:** 30 minutos

  if (!frameId) return tpl.canvas.objects;

  if (!frame) return tpl.canvas.objects;

El rate limiting mencionado en CAT1-3 (H5: "429 en ~40 requests/min") probablemente proviene de Netlify global rate limiting, no de la aplicación.

Nota: hay un middleware `api/src/middleware/rateLimit.ts` en el filesystem. Pero el MCP endpoint (`netlify/functions/mcp.mjs`) es una Edge Function separada que NO usa Express ni middleware de la API. Corre standalone.

**Funciones a modificar:**
- `handleRequest()` o `handler()` — entry point del endpoint MCP

**Approach:**
1. Como las Edge Functions son stateless, usar un Map en memoria para rate limiting por IP:
   ```js
   const rateLimitMap = new Map(); // IP → { count, resetTime }
   const RATE_LIMIT = 60; // requests per window
   const RATE_WINDOW = 60_000; // 1 minute in ms
   
   function checkRateLimit(ip) {
     const now = Date.now();
     const entry = rateLimitMap.get(ip);
     if (!entry || now > entry.resetTime) {
       rateLimitMap.set(ip, { count: 1, resetTime: now + RATE_WINDOW });
       return true;

     if (entry.count >= RATE_LIMIT) return false;
     entry.count++;
     return true;
   }
   ```

   ```js
   const ip = request.headers.get("x-forwarded-for") || "unknown";

     return new Response(JSON.stringify({ jsonrpc: "2.0", error: { code: -32000, message: "Rate limit exceeded. Try again in 60s." } }), { status: 429 });
   }
   ```
3. La ventana de 60s con 60 req/min es conservadora. En Netlify Edge, el Map sobrevive mientras la función está caliente (misma instancia), lo cual es aceptable para MVP.

**Riesgo de BD:** NO — rate limiting puramente en memoria.

#### CORRECCIÓN LARA: P0.1 — `em()` precision fix

**Problema con el approach de Qoder:** `n.toFixed(1)` solo preserva 1 decimal. Para diseño, necesitamos al menos 2 decimales (ej: border-radius 0.25px, opacity 0.33). `toFixed(1)` mostraría 0.3 para 0.25.

**Approach corregido:**
```ts
// Display: preservar hasta 2 decimales, eliminar ceros sobrantes
const em = (n: number) => {
  if (n == null || isNaN(n)) return "0";
  return parseFloat(n.toFixed(2)).toString();
};
// Para commit: usar Number(val) crudo, SIN pasar por em()
```

**Riesgo de BD:** NO confirmado — mismo veredicto que Qoder.

#### CORRECCIÓN LARA: P0.3 — Frame persistence

**Problema con el approach de Qoder:** Qoder propone crear el objeto visual después de `store.createFrame()`. Pero el flujo actual tiene un bug: `store.createFrame()` hace `tpl.frames.push(frame)` y `tpl = store.updateTemplate(id, { frames: tpl.frames })`. El nuevo objeto visual DEBE agregarse a `tpl.canvas.objects` y persistirse en la MISMA operación.

**Approach corregido:**
```js
case "create_frame": {
  // 1. Crear frame en metadata (como antes)
  const frame = await store.createFrame(params.templateId, params.name, params.x, params.y, params.width, params.height, params.fill);
  
  // 2. Crear objeto visual EN EL MISMO template canvas
  const visualObj = {
    type: "rect",
    layerName: `frame_visual_${frame.id}`,
    frameId: frame.id,
    isFrameVisual: true,
    left: params.x || 0, top: params.y || 0,
    width: params.width || 400, height: params.height || 300,
    fill: params.fill || "#ffffff",
    stroke: "#6366f1", strokeWidth: 1,
    rx: 0, ry: 0, opacity: 1, visible: true,
  };
  
  // 3. Agregar al canvas EXISTENTE y persistir
  const tpl = await templates.getTemplate(params.templateId);
  tpl.canvas.objects.push(visualObj);
  await templates.updateTemplate(params.templateId, { canvas: tpl.canvas });
  
  // 4. Devolver frame con frameId consistente (fix BUG-011)
  return { frameId: frame.id, name: frame.name, ...frame };
}
```

**Riesgo de BD:** BAJO confirmado — agrega objetos a `data.canvas.objects[]` (JSONB existente).

#### CORRECCIÓN LARA: BUG-017 — Transparent background

**Problema con el approach de Qoder:** Hacer el fondo transparente por defecto rompe el comportamiento actual. Muchos templates asumen fondo blanco. El cambio debe ser un PARÁMETRO OPCIONAL en `render_batch`, no un cambio de default.

**Approach corregido:**
```js
// En render_batch handler, nuevo param opcional:
// transparent: boolean (default false)
const backgroundColor = params.transparent ? "transparent" : (template.backgroundColor || "#ffffff");
const canvas = new fabric.StaticCanvas(null, {
  width, height,
  backgroundColor: backgroundColor,
  renderOnAddRemove: true
});
```

**Riesgo de BD:** NO confirmado.
