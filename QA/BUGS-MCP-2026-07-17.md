## 🔴 BUG-CRLF-001 (NUEVO — P0)

**Tool:** `create_template` / `update_template` (engine html)
**Síntoma:** Si el parámetro `css` contiene line endings CRLF (`\r\n`), el server responde:

```json
{"code":-32000,"message":"css2.match is not a function"}
```

**Repro:**
1. `create_template` con `css: ".x { color: red; }"` (LF) → ✅ OK (tpl creado)
2. Mismo payload con CSS leído de archivo Windows (CRLF) → ❌ error -32000
3. Mismo CSS con `\r\n` reemplazado por `\n` → ✅ OK

**Evidencia:** TEST D (falla, CSS con CRLF) vs TEST F (pasa, mismo CSS con LF), templates de prueba `tpl_b92f5187-6d3` (F, ya borrado).
**Hipótesis:** el server hace split por `\n` y alguna línea con `\r` residual convierte `css2` en algo que no es string (probablemente en el parser de @import/fonts). El nombre de variable `css2` sugiere procesamiento del import de Google Fonts css2.
**Impacto:** Cualquier cliente Windows que mande CSS de archivos sin normalizar falla con error críptico.
**Fix sugerido:** `css = String(css).replace(/\r\n?/g, '\n')` al inicio del handler + coerción defensiva a string.
**Workaround actual:** normalizar a LF client-side antes de llamar.

## 🟡 BUG-RENDER-JSON-002 (NUEVO — P1, gap conocido con síntoma nuevo)

**Tool:** `render_batch` + `POST /api/templates/:id/render`
**Síntoma:** `render_batch` responde `status: ready` con `_links.render`, pero ese endpoint NO devuelve PNG binario: devuelve JSON con una página HTML que usa **html2canvas client-side** (el render real ocurre en el navegador del usuario).
**Impacto:** No hay forma programática de obtener un PNG del server. El gap `render_frame`/render server-side sigue abierto (ya estaba en `20_PRIORIDADES_MCP.md`), pero ahora confirmado que `render_batch` tampoco lo resuelve — solo "prepara" links.
**Workaround actual:** render local con Puppeteer usando el mismo html/css del template (script reusable: `C:\Users\Renzo\.openclaw\workspace\tmp_munx\render_local.js`). Resultado idéntico al diseño.
**Fix sugerido:** endpoint server-side con Puppeteer/Playwright en función serverless (o servicio externo tipo Browserless) que devuelva `image/png`.

## 🔴 BUG-UPDATE-NOOP-004 (NUEVO — P0)

**Tool:** `update_template` con parámetros top-level `html`/`css`
**Síntoma:** El server responde 200 con el template completo, pero **el contenido del frame NO se actualiza**. Es un no-op silencioso.
**Repro (2026-07-17):**
1. `update_template { id, html: '<!--UTF8MARKER áéñ-->...', css }` → respuesta OK
2. `get_template { id }` → el marcador **no existe** en `frames[0].html` (ni en UTF-8 correcto ni en mojibake — simplemente no se escribió)
3. `update_template { id, frames: [{ id, name, x, y, width, height, html, css, background }] }` → ✅ el contenido SÍ se actualiza

**Impacto:** La API documenta `html`/`css` como "HTML content for active frame" pero es mentira — cualquier cliente que confíe en esa ruta cree que guardó y no guardó nada. Peor tipo de bug: falla silenciosa.
**Workaround:** usar SIEMPRE `frames[]` completo (leer el template con `get_template`, modificar el frame, mandar el array entero).
**Fix sugerido:** implementar la ruta html/css → frame activo, o eliminar los params del schema para no mentir.

## 🟡 OBS-FRAME-IDS-005 (menor)

**Tool:** `update_template` con `frames[]`
**Síntoma:** Si los frames del array no traen `id`, el server los guarda **sin id** (`get_template` devuelve frames con `id` ausente). No autogenera ids.
**Impacto:** frames sin id probablemente rompen selección/edición en el editor.
**Workaround:** generar ids client-side con formato `frame_xxxxxxxx-xxx`.
**Fix sugerido:** autogenerar id server-side cuando falte.

## 🔴 BUG-STATE-CHAOS-007 (NUEVO — P0, agrava el 003)

**Síntoma:** Estado inconsistente entre requests consecutivos (instancias serverless con memoria divergente):
1. Templates borrados en la sesión (TEST A/B/D) **resucitaron con IDs nuevos** (`tpl_18e8739c-15a`, `tpl_8b82ad96-cb3`, `tpl_a2bb95cb-f56`).
2. Los templates individuales MUNX cambiaron de ID entre requests (`tpl_0da96e2c-301` → `tpl_2046b1c6-d01`, etc.): `delete_template` con el ID original da "Template not found" mientras `list_templates` lo muestra con ID nuevo.
3. Minutos después, otro `list_templates` mostró solo el kit — los zombies desaparecieron solos, sin que ningún delete tuviera éxito.
**Evidencia:** logs de `consolidate.js` y `cleanup_final.js` (2026-07-17 ~21:15-21:20).
**Hipótesis:** hay algún nivel de rehidratación (¿Supabase?) que regenera IDs al cargar, y cada instancia Edge mantiene su propio Map en memoria → lecturas/escrituras caen en instancias distintas según el request.
**Impacto:** IDs no son estables → imposible automatizar nada de forma confiable; deletes y updates pueden caer en una instancia y perderse.
**Fix sugerido:** una sola fuente de verdad (DB) para TODA lectura/escritura; eliminar el Map en memoria o usarlo solo como caché con IDs persistidos.
